# Технічне завдання та межі дослідження (v1.0)

## Тема і дослідницька гіпотеза

Мета: експериментально оцінити, чи може ML-персоналізація модуля вебпанелі зменшити час та кількість дій у типових задачах за умови збереження доступності й контролю користувача. **Це гіпотеза, а не готовий висновок.**

## Головний об'єкт: modular dashboard

Віджети: `tasks`, `calendar`, `activity`, `quick_actions`, `reports`, `notifications`. Для кожного UI-варіанта доступний той самий набір функцій. Дозволені зміни: порядок віджетів, щільність карток (без приховування важливих можливостей), акцент на пріоритетному віджеті; заборонено руйнувати навігацію, клавіатурний доступ та зміст.

- `standard`: універсальний порядок і звичайна щільність.
- `compact`: компактні картки, ті самі дії, приорітет швидким діям і задачам.
- `focus`: одна чітка провідна зона задач, решта модулів збережені й доступні.

Гарантована панель навігації не переставляється. Усі макети проходять тести без ML.

## Функціональні сценарії

1. Перший запуск: статичний інтерфейс, збір подій вимкнений.
2. Добровільне ввімкнення аналітики; користувач бачить коротко: що, для чого, строки, як відкликати.
3. Реєстрація дозволених подій `widget_open`, `task_start`, `task_complete`, `quick_action`, `layout_preview`, `layout_accept`, `layout_reject`, `layout_undo` без записування тексту/URL.
4. Запит рекомендації й вибір алгоритму; відображення політики, рівня впевненості та причин fallback.
5. Preview, явне підтвердження, Undo, вимкнення, видалення профілю.
6. Режим дослідження: виконання наявних завдань зі стандартним сценарієм та експорт consented спостережень.

## Алгоритми

- S0 `static`: завжди `standard`.
- S1 `rule`: прозорі, заздалегідь записані правила на довідкових ознаках; до порівняння визначені пороги.
- M1 `logistic_regression`: Multinomial/автоматичний багатокласовий LR із препроцесингом.
- M2 `random_forest`: багатокласовий класифікатор.
- M3 `xgboost`: `XGBClassifier`, якщо встановлено. Не заміняти ним інший або навпаки непомітно.
- H1 `hybrid`: обрана ML-модель + обмеження + підтвердження користувача.

Мітка `preferred_layout` в реальному протоколі має походити від **добровільної задокументованої оцінки користувача**, проведеної окремо від контрольованого вимірювання UX. У synthetic generator псевдомітки створюються лише для тестування.

## Межі MVP

Не потрібні облікові записи реальних людей, хмарний деплой, LLM, комп'ютерний зір, платні API, збір особистої переписки, прихований трекінг чи «штучні учасники». Локальний запуск і експорт доказів важливіші за фічі.

## Критерії успіху ПЗ

- Повністю працює без ML (static fallback).
- Навчання, тестування й оцінювання відтворюються за фіксованими seed.
- Експерименти не змішують поточні/майбутні результати UX з pre-decision ознаками.
- Є реальні машинні виходи (не намальовані таблиці), тести й документи для магістерської.
- Жоден запуск із synthetic даними не позиціонується як дослідження реальних людей.
