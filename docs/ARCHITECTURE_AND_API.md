# Рекомендована архітектура та контракти API

## Компоненти

```
React + TypeScript + Vite
   |   opt-in interaction events, tasks, previews
   v
FastAPI REST + Pydantic validation
   |-- event service (consent + TTL)
   |-- layout service (three verified variants)
   |-- recommendation service (baseline/rule/ML/policy)
   |-- study service (experimental trials)
   |-- export service (aggregate metrics, delete)
   v
SQLAlchemy ORM --> PostgreSQL (SQLite unit-test mode)
   |
   +--> ML package: features -> group split -> pipelines -> scoring -> model registry
   +--> reporting: CSV, JSON, PNG, SVG, MD, logs
```

## Обов'язкові сутності БД

`AnonymousParticipant`, `ConsentRecord`, `InteractionEvent`, `LayoutState`, `Recommendation`, `StudyTrial`, `ModelRun`, `ModelArtifact`. Установи primary/foreign keys, created timestamps, індекси, TTL і unique constraints де потрібно. Не створювати в БД особисті профілі з реальними іменами.

## Мінімальний REST API (усі шляхи версіоновані `/api/v1/`)

- `GET /health`: `status`, `version`.
- `GET /layouts`: допустимі layouts, order та capabilities (усі функції доступні).
- `GET /consent`: статус згоди для анонімного учасника.
- `POST /consent`, `DELETE /consent`: добровільне ввімкнення/відкликання, при DELETE зупинити збір; окремий спосіб видалення старих подій.
- `POST /events`: прийняти лише schema-valid події за `consent=true`, інакше 403/no persist.
- `POST /recommendations`: передати features snapshot або session і поточний layout; повернути decision за `contracts/prediction.schema.json` (без прихованого переключення).
- `POST /recommendations/{id}/accept`, `POST /recommendations/{id}/reject`, `POST /recommendations/{id}/undo`: ідемпотентні контрольовані переходи стану.
- `POST /study/trials`: добровільна реєстрація фактичної спроби з показниками.
- `GET /export/me`, `DELETE /profile/me`: дані учасника і видалення.

У коді використай OpenAPI autogenerated schema; реалізуй права доступу до власного випадкового псевдопрофілю (токен, session secret чи еквівалент, але не просте user_id в URL без перевірки). На localhost demo не виставляй бінд 0.0.0.0 без необхідності. Документуй CORS і CSRF при cookie-based sessions.

## UI контракти

- `current_layout` зберігається між сесіями (локально або у БД відповідно до consent), але не змінюється без `accept`.
- Усі варіанти мають один data-testid на однакові дії для E2E.
- Перший рендер доступний без бекенду завдяки static fallback.
- Користувач може повернути попередній стан навіть якщо API недоступний; після відновлення зв'язку відбувається узгодження.
- Окрема панель `Research mode` з явною позначкою `DEMO / SYNTHETIC` для інженерної демонстрації.
