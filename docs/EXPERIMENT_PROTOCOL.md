# Протокол дослідження для розділу 2 та розділу 4

## Два незалежні види оцінки

**Offline ML quality (розділ 2):** чи може модель передбачити користувацьку перевагу між `standard`, `compact`, `focus` за ознаками, наявними до рішення? Метрики: accuracy, macro-precision, macro-recall, macro-F1, logloss (за наявності всіх класів і `predict_proba`), confusion matrix, coverage. Порівняння має включати статичний та rule baseline; для них logloss допустимий лише за явно заданого валідного і задокументованого способу отримання розподілу ймовірностей.

**Controlled UX evaluation (розділ 4):** чи змінює вибір інтерфейсу час, успішність, кількість дій та сприйняття керованості для добровільних реальних учасників? Це **інший дослід**, він не дорівнює offline accuracy.

## Формування мітки й ризик упередженості

Рекомендовано 2 етапи добровільного дослідження:

1. **Pilot/preference collection:** продемонструвати людині всі три повнофункціональні варіанти у збалансованому порядку, зібрати явно обраний `preferred_layout` і причини (якщо причини включають текст, зберігати тільки узагальнені категорії). Прогнозні ознаки рахувати ЛИШЕ із попереднього дозволеного періоду спостереження (timestamp < recommendation_time), без відповіді на анкету та без майбутньої успішності. Записати кількість людей, умови збору, пропуски.
2. **UX study:** на іншій когорті або за чітко розділеними етапами застосувати умови `static`, `rule`, `hybrid` (порядок учасників урівноважений, але якщо дослід малий — подати обмеження); сценарії однакової складності/усі функції однакові. Моделі заморожені до досліду. Не робити висновок про причинність з offline train/test.

**Увага:** якщо реальних позначених прикладів недостатньо для 3 класів і group split, позначити `MODEL_NOT_EVALUABLE`; не обчислювати фіктивні метрики на synthetic dataset як емпіричні висновки.

## Одиниці даних

- `participant_id` — випадковий псевдонім для групування; не email, не ПІБ.
- `session_id` — випадковий ID сесії.
- `event` — дозволена подія з типу enum, без тексту користувача.
- `preference_label` — явно добровільно обраний макет, `label_source=explicit_preference`.
- `trial` — одна спроба задачі при певній умові з `elapsed_ms`, `click_count`, `completed`, `error_count`, `sequence_index` та `is_synthetic`.

## Ознаки (до decision_time)

`opens_tasks_7d`, `opens_reports_7d`, `quick_actions_7d`, `avg_actions_per_session_7d`, `active_sessions_7d`, `last_device_category`, `last_viewport_category`, `time_of_day_bin`, `prior_undo_rate`, `current_layout`, `active_task` (тільки контроль політики). Контекстні категорії перелічені наперед; не зберігати точні координати, URL, введені тексти, IP чи user-agent.

## Поділ та модель

- Primary split **participant-disjoint**: учасник ніколи не буває одночасно train/validation/test. Рекомендовано приблизно 60/20/20 за учасниками, але фактичний розподіл та класову повноту обов'язково зафіксувати.
- Preprocessing й вибір ознак (`fit`) тільки в межах train; tuning — validation, final test — лише один раз. Якщо часу/учасників мало, пояснити обмеження потужності. Задокументувати temporal provenance, перевірити, що на момент передбачення не використано інформацію із майбутніх подій. Окремо, якщо можливо, додати time-based sensitivity analysis із фіксованим cutoff без перетину учасників.
- Метрики offline по учасниках (не тільки по сесіях) — додати довірчі інтервали через bootstrap at participant level **лише якщо** це коректно для числа груп; інакше описові статистики.
- Не стверджувати, що higher F1 автоматично означає faster UX.

## Гібридна політика — конфігурація за замовчуванням (можна дослідити зміни)

- `min_events=5` (холодний старт → залишити current або standard).
- `min_confidence=0.55` та `min_probability_gain=0.15` відносно current layout; задокументувати що це ймовірності від класифікатора, а не гарантоване підвищення UX.
- `cooldown_hours=24` після підтвердженої зміни, `no_change_during_active_task=true`.
- `user_confirmation=true`, `undo=true`, `can_disable=true`, `required_widgets_always_visible=true`.
- Параметри політики не підганяти за test subset; провести абляцію: ML only / +threshold / +threshold+stability+control. Для порівняння policy показувати coverage, рекомендації, відхилення, fallback, change count, а не вигадану перевагу в UX.

## UX-протокол (тільки реальні учасники)

Три стандартизовані задачі (приміром, знайти завдання, відкрити звіт, скористатися швидкою дією), функціонально тотожні у всіх умовах. Фіксувати порядок/умову/час/дії/успішність/помилки. Збирати SUS тільки якщо учасник справді заповнив всі 10 запитань. Звітувати N учасників, N спроб, розкид, медіану та IQR, можливі інтервали невизначеності й ефекти навчання. Статистична значущість — лише за валідного дизайну та вибірки.
